## Milestone 0 integration requirements and open gates

1. **Feature switch and recovery:** add default-false `markdownLiveRenderTables.markdownRendering.enabled`; reconfigure the parser/presentation in place. Preserve base Markdown input, tables, clipboard, pending source edits, and host acknowledgements while disabling. A plugin failure must leave a usable base editor, not only an error-free console.
2. **Measured marker prototype:** bullets/tasks/rules need exact shaped marker advance without adjacent whitespace, bounded scheduled measurement, literal fallback for wrapped/bidi/unsafe geometry, no extra atomic ranges, and refresh when syntax/geometry becomes ready. Prove actual following-text glyph boxes, wrap points, document height, and scroll position before/after reveal, including tabs, letter spacing, font size, zoom, and viewport width.
3. **Task source action:** one ASCII code unit, revalidated against current optimistic source and `getParsedTables`, one collapsed effective caret or explicit focused control. Reject while composing; do not append task actions to the undo-command composition queue. Feed ordinary validated edits through the existing host queue. Test two rapid toggles interleaved with typing, table edits, rejections, external edits, and disable.
4. **Read-only capability and rejection:** establish supported host state, propagate it to new actions, recheck at dispatch/acceptance, and test an actual host rejection against the current dirty document. A DOM-only disabled state is insufficient. Filesystem capability, file permissions, configured/session overrides, and final `WorkspaceEdit` acceptance need explicit coverage/limitations.
5. **Task focus and accessibility:** preserve the invoking editor context across the Command Palette, map source bookmarks through changes, use programmatic focus without thousands of Tab stops, and release only owned focus on eviction/disable/ownership changes. Observe the host screen-reader body class and test with an actual screen reader. Never restore a bookmark inside protected table source or overwrite a newer source selection.
6. **Isolation and incremental work:** classify through one configured Markdown tree, then exclude tables from every mark, line treatment, replacement, and action. Measure source identity independently from host revision. Selection/focus-only updates must avoid whole-document parsing and source materialization. Preserve table DOM during theme updates and cell edits.
7. **Host history proof:** use an actual active custom editor and host acknowledgements; synthetic `setDocument` snapshots and local transaction annotations cannot prove one host Undo per toggle. Existing host command routing should be reused, with queue settlement on rejection/disposal.

## Performance evidence still required

At the initial baseline review, no latency or new-renderer benchmark had been run. The 10,011-line gutter contract verifies fixture/table correctness; it does not measure the specification's p50/p95/max update cost, input-to-paint latency, memory growth, or parse convergence. The subsequent CPU-only benchmark is recorded below; browser/host performance validation remains incomplete.

`getParsedTables` caches by immutable document object but scans each new snapshot (`src/shared/tableModel.ts:59-83`). Webview edits transmit complete before/final text claims. These are baseline costs to measure, not redesign implicitly during this feature.

Before releasing, measure the same build with rendering disabled/enabled over 10,000- and 100,000-line mixed fixtures, including 2,000-character lines and distant structural openers. Run at least 200 edits, 100 selection/focus changes, and 100 scroll updates per fixture. Report classes separately with p50/p95/max, total input-to-next-paint latency, cold parse convergence, and memory/DOM/cache behavior after scroll/theme cycles. Include parsing, layout/paint, widgets, scheduled measurement, and deferred work. The required added-update p95 budgets are 8ms/16ms, with at most a 16ms p95 input-to-next-paint increase. No claim against those budgets is made here.

Implementation validation, final build/install verification, and any completed prototype gates should be appended as new evidence or linked from a subsequent implementation report. This baseline record is not a substitute for those results.

## Prototype implementation and current evidence

The implemented slice is the **Milestone 0 prototype**, behind the default-false rendering switch. It adds parser-classified unordered bullet/task/rule presentations, exact task source edits through the existing host queue, Command Palette toggle/focus actions, source-bookmark focus recovery, known filesystem read-only awareness and host revalidation, accessibility-mode literal fallback, and switch/failure recovery. Source text retains shaping and navigation ownership; the visual marker layer uses inline marks and controls that do not allocate new source width. Tables keep their existing ownership. This is not the readable-source, general interaction, multiline-rendering, or default-release milestone.

The focused [actual-host test script](../scripts/edh-markdown-rendering-check.mjs) opens a fresh VS Code profile, enables rendering/debug explicitly, writes only its temporary Markdown fixture, and runs trusted CDP keyboard/pointer events against the live webview. It verifies acknowledgements and invokes real VS Code Undo. It does not synthesize authoritative document snapshots for host-history checks. It captures `Runtime.consoleAPICalled` and `Runtime.exceptionThrown`, not only extension debug events.

Latest focused main run: **25/25 checks passed**, [results](edh-markdown-rendering-results.json), isolated profile `mlrt-markdown-edh-s9klrT`. This includes six lifecycle/accessibility-mode checks added during the requested continuation after the initial nineteen-check run; their results are detailed below. ### CPU characterization after implementation

The [CPU benchmark script](../scripts/benchmark-markdown-rendering.mjs) produced [inspectable samples and methodology](markdown-rendering-cpu-baseline.json). It runs 160 local edits, 40 structural edits, 100 selection updates, and 100 simulated viewport classifications for each mode/fixture after separate warm-up. Fixtures contain 10,000/100,000 lines, 210/2,100 tables, long lines, and offscreen structural openers. Parse convergence work is included in its operation CPU totals; immutable `Text` identity and table cache reuse are checked for source-preserving operations.

| CPU result | 10,000 lines | 100,000 lines |
| --- | --- | --- |
| Baseline local-edit total p95 | 2.8179ms | 32.2923ms |
| Enabled local-edit total p95 | 2.9578ms | 35.2377ms |
| Baseline structural-edit total p95 | 14.9804ms | 200.4739ms |
| Enabled structural-edit total p95 | 19.4263ms | 267.0853ms |
| Enabled selection total p95 | 0.0748ms | 0.4315ms |
| Enabled simulated viewport total p95 | 0.0603ms | 0.4553ms |
| Enabled cold initialization/convergence total | 21.5669ms | 238.2074ms |

The pure added classifier's largest p95 across the 100,000-line operation classes was 0.6387ms. The much larger extended-parser/structural-edit cost is a **material release concern**: the enabled structural p95 is 267.0853ms versus 200.4739ms in the baseline, before DOM/paint/host work. This sequential CPU comparison is not a controlled end-to-end rendering delta, but it cannot be dismissed because the classifier alone is small. A release needs measured mitigation or an evidenced plan for these slow structural paths and baseline full-snapshot work.

This benchmark excludes EditorView/widgets, scheduled geometry measurement, layout/paint, actual input-to-next-paint, VS Code synchronization/full-text claims, actual focus/scroll/theme/IME events, and retained DOM/cache/heap behavior. It does **not** pass the 8ms/16ms added-rendering or 16ms input-to-next-paint budgets. Sample counts and low classifier CPU cost are not substitutes for that missing evidence.

### Historical prototype gate decision

**Milestone 0 remains incomplete and rendering stays default false.** The prototype now has focused evidence for viewport eviction, mapped focus recovery under external replacement, newer selection preservation, and host accessibility-mode fallback, as well as the source/geometry/task/recovery checks above.
